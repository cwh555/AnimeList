# AnimeList Protocol

This is the authoritative agreement for language boundaries and compatibility. Markdown and YAML frontmatter remain the source of truth.

## Language boundaries

AnimeList interface locales: zh-TW, zh-CN, en, ja, ko.

| Surface | Language behavior | Storage |
| --- | --- | --- |
| Workspace UI, buttons, notices, forms | Localize through i18n catalogs | No data rewrites |
| **Obsidian Settings and Settings-launched dialogs** | **Always English, including progress and errors** | No localization of Settings prose |
| Provider-category tags in the known dictionary | Translate labels for display | Keep original canonical values |
| User tags and custom text | No automatic translation | Preserve input |
| Author/studio/creator names | No automatic translation | Preserve source/user text |
| Newly imported work titles | Select known provider-labeled title for interface locale | Persist chosen title and provenance |
| Existing note titles | **Never change on interface locale switching** | Persist until user explicitly edits or migrates |

Legacy tag limitation: historical genres mixes provider terms and manually entered tags. A user tag that equals a recognized provider dictionary key may display a localized label even though the stored value is unchanged. Resolving such ambiguity requires a separate source-provenance migration.

## Title provenance

- title: current stored/user-controlled title.
- title_original: source-original title.
- title_romaji: romanized spelling when available.
- title_aliases: historical names and search aliases.
- title_localizations: optional locale-to-verified-title dictionary from the provider.
- title_script_conversions: optional locale-to-OpenCC-converted-name dictionary, written **only after the user explicitly accepts a suggestion**. It never claims the conversion is official, and allows round-trip selection without mistaking the previously accepted result for an unknown custom title.

Bangumi name_cn is Simplified Chinese, not necessarily an official Taiwanese Traditional title. A verified Traditional title must have explicit provenance from Bangumi infobox. AniList provides English/native/romaji, with JP/KR native attribution only if origin information supports it. Never invent an official translation from unlabelled synonyms. OpenCC (opencc-js 1.4.2) is available **only** as an offline Chinese-script-conversion fallback. It is **not** a provider-verified localized title or general machine translation.

## Cleanup responsibilities

- **Version updates**: fixes for artifacts generated by older plugin templates (e.g. duplicate default cover embeds).
- **Legacy data**: opt-in changes to user-owned notes (filenames, metadata and localized titles).

## Existing-title update workflow

Settings → Updates & cleanup → Existing media titles → Preview title updates.

1. User selects target language; *all* Settings dialogs, button labels, status messages and errors remain English.
2. The scanner shows each work's name, path and result as it completes. All scanned work results remain visible in the review list, not just proposals.
3. Title candidates come from previously verified stored localizations, exact provider IDs, or exact provider IDs preserved in source URLs. Bangumi title-only requests omit the separate person/studio endpoint.
4. For an AniList-only work needing a Chinese name, a unique original-title matching Bangumi search result can be proposed **for explicit review only**. Ambiguous or mismatched-year results are rejected; such proposals are unchecked by default.
5. Every work has a scan status: ready, review, unchanged, no-source, no-translation, custom-title, ambiguous, or lookup-failed. Live scanning shows each status; the completed review lists **only actionable changes**, with aggregate counters for other outcomes. A Bangumi result with Simplified Chinese but no verified Traditional Chinese title may provide an OpenCC conversion as an **unchecked review-only proposal**; the UI must never mislabel it as an official translation. No Chinese source means a visible missing-translation status.
6. The user reviews old → proposed name and selects works. Preview never writes.
7. On apply, recheck source identity, original title and file modification time. Write only title, optional missing title_original, title_aliases, title_localizations and accepted title_script_conversions, through Obsidian processFrontMatter.
8. Do not alter filenames, Markdown bodies, headings, personal scores, progress, authors, tags, covers, rankings, or unrelated YAML. This protects Obsidian links and note ownership.
9. Each write outcome is reported. Closing the modal after confirmation does not cancel already-running writes, and a final notification still appears.

Requests are paced with shared minimum spacing (350ms by default) and bounded concurrency (three workers by default, maximum four); duplicate provider IDs are fetched once per scan. API failures are shown with their work and reason, never silently swallowed.

## Compatibility

Older notes without title_localizations remain usable and are not automatically modified. Changing the interface language must never trigger a data migration. Filename reconciliation is an entirely separate, manually previewed compatibility tool.

Human Test Vault validation must additionally check Settings English, large-library scanning responsiveness, and exact update previews.

## Provider-neutral title selection

A single typed selector owns the rules in `src/domain/media-title-localization.ts`. The data adapter in `src/data/media-title-service.ts` applies it to `ExternalMediaResult`, without modifying source identity, metadata, author/studio names, or authoritative title variants. Each provider normalizer **only extracts title evidence**; all three then use the same adapter. The create-note enrichment boundary reapplies this selection before the form is populated, so a second API call cannot silently revert the name.

For **new** imports, in order:
1. Prefer an explicit, provider-labelled title for the interface locale.
2. Use a localized Wikidata/Wikipedia name **only when a unique QID is linked by the work's exact AniList/Bangumi external ID**. Record QID, locale and source separately in `title_external_evidence`—not in the provider-verified `title_localizations` map.
3. If the locale is Chinese and the source has an explicitly labeled name in the other Chinese script, use offline OpenCC as a fallback. Record the conversion in `title_script_conversions`, **never** `title_localizations`.
4. Otherwise keep a safe source title. Unlabelled synonyms are searchable aliases, not verified translations; do not infer a work's identity from its title.

Provider-specific evidence:
- **Bangumi:** `name_cn` is Simplified Chinese, an explicitly labelled infobox title can be Traditional Chinese. Both can be converted when the other script is requested.
- **AniList:** `english` is official English; `native` is attributed to its native-script locale when `countryOfOrigin` identifies JP, KR, CN, TW or HK. Chinese-origin native titles can use script conversion, with conversion provenance recorded separately. Country-of-origin attribution is not evidence of a separate licensed translation. Neither `romaji` nor `synonyms` provides trustworthy Chinese language attribution for Japanese/Korean-origin works, so do not invent Chinese translations.
- **Open Library:** Work `title` is a fallback, not presumed to be an official Chinese translation. Search's `lang` now follows the interface's language preference (zh-TW/zh-CN → zh, en → en, ja → ja, ko → ko), which influences edition preference but **does not certify the title language**.
- **Manually entered media:** User-entered title is authoritative; the adapter skips manual items entirely.

This contract applies to search results, metadata enrichment, and the initial creation form; no legacy-data action is needed for new imports. If the user changes the suggested title manually before saving, the note stores that exact title and does not falsely claim a script conversion. `title_original`, `title_aliases`, verified `title_localizations`, and actual creators are preserved.

Cross-provider matching by title/year is **not** sufficient evidence to auto-fill verified titles. Legacy title reconciliation can offer potential cross-provider matches for explicit review, but a new import must not silently adopt an unverified match. Machine translation is not currently provided.

## AniList API availability and request contract

AniList's official API documentation (https://docs.anilist.co/guide/rate-limiting and https://docs.anilist.co/guide/considerations) describes a temporary degraded limit of **30 requests/minute**, burst limits, 429 responses with Retry-After, and 403 responses while the API is disabled for stability. AniList may also exceptionally block excessively active IPs. No API client can guarantee availability during an upstream outage.

All AniList GraphQL calls, including search, exact-ID enrichment and manga release links, use the single POST endpoint `https://graphql.anilist.co`. `AniListClient` coalesces duplicate in-flight queries, maintains a bounded response cache and **serializes different-key HTTP calls** with at least 2100 ms between request starts. Search query variants are batched through GraphQL aliases when supported, rather than launching one HTTP request per variant.

For HTTP 403 / GraphQL status 403: do not retry, bypass the upstream restriction or switch to an undocumented proxy. Surface the provider error and stop additional requests from the same client for a 60-second cooldown; queued calls fail without contacting AniList. 429 follows `Retry-After` where provided, otherwise pauses 60 seconds; retry only once when the remaining delay is short enough for interactive use. An interactive request timeout also causes a temporary cooldown, because Obsidian's `requestUrl` has no physical abort capability. 5xx may be retried at most once. Other providers are independent and remain searchable.

This is intentionally **request-load mitigation, not a claim to fix AniList's server-side 403 availability**. Offline unit/contract tests simulate successful calls, 403, 429, timeouts and queued workloads; real-user network conditions and upstream outages require manual observation.

## Unified language evidence via Wikidata / Wikipedia

The title resolver is independent of the metadata provider. First prefer a title explicitly labeled for the selected interface language in the original provider; then look up a **unique Wikidata entity through the exact external work ID**, rather than choosing the first text-search result; then use Chinese script conversion from a reliably labeled Chinese variant; finally retain the source name. English/Japanese/Korean aliases without language attribution are *not* Chinese translations.

The supported Wikidata property mapping is AniList anime `P8729`, AniList manga/light novels `P8731`, and Bangumi subjects `P5732`. The resolver queries WDQS for a unique `QID` (rejecting absent/duplicate matches) and retrieves localized labels and Wikipedia sitelinks with `wbgetentities`. The QID, identifying property, text, locale and source category are recorded as `title_external_evidence` only when that title is chosen. A Wikidata label or Wikipedia article name is **community-curated multilingual naming evidence**, not necessarily an official licensed release title; script-converted variants are labeled separately. The `title_localizations` map remains reserved for provider-labeled variants.

The same identifier-based Wikidata service is used in the **new-note** enrichment flow and the existing-note Title Update **review** flow. The separate legacy-metadata repair flow requests **classification only**, so it does not add Wikidata/Bangumi title lookups for every note being migrated. New-note defaults may adopt a unique QID-linked name; existing notes are *never rewritten automatically*. A title/year-only Bangumi matching heuristic remains a review-only last resort, never a verified cross-provider identity. Manually entered or edited names remain authoritative. If Wikidata is unavailable or has no exact ID link, preserve the provider title rather than inventing a translation.

Do not infer completeness from a name search: not all Wikidata items carry AniList/Bangumi properties. Queries should be narrowly scoped to one external ID, cached by property/ID/locale, and should not be retried aggressively on upstream errors. See [Wikidata data access guidance](https://www.wikidata.org/wiki/Help:Data_access).

## Incremental Settings operations

All four operations in **Updates & cleanup** expose the same scan-scope choice:
- **Only new or unfinished items** (default): skip successful checks whose file mtime/size and operation have not changed. Title checks additionally distinguish target language. Proposed but unconfirmed changes and API errors remain pending.
- **Rescan all items**: ignore checkpoints and inspect all eligible notes in the configured Library roots.

Checkpoints reside in `.obsidian/plugins/animelist/cleanup-scan-history.json` and are not frontmatter, not part of the note body, and not a record of media activity. Each successful write is checkpointed against the **updated** file version so the new file content is not immediately rescanned. Failed writes, inconclusive provider upgrades and unconfirmed proposals are never marked complete. A separate full scan remains available whenever the upstream metadata source changes. File moves/renames and content edits naturally invalidate path/version-based checkpoints. No scanning runs automatically merely because Settings was opened.
